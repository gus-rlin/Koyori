# Étape 2 — mémoire et connecteurs contrôlés

Contrats `schemaVersion=1.0`, 2026-10-05. Cette livraison ajoute des commandes explicites au socle. Planification naturelle, apprentissage inféré, MCP et voix restent aux étapes 3 et 4. [Preuves et limites](verification/stage2.md).

## Mémoire et contexte

`POST /v1/memories` conserve un échange finalisé, une préférence (`key` obligatoire) ou une procédure déclarative (`key` et `steps` obligatoires). Chaque souvenir porte propriétaire, auteur/canal serveur, origine, date, visibilité, validité, révision et époque de confidentialité. L'attribution HTTP actuelle est personnelle ; l'admission de tours d'un appareil vocal partagé appartient à l'étape 4. Les appareils partagés lisent seulement les souvenirs explicitement partagés. Les engagements sont dérivés des tâches/actions canoniques, jamais déclarés comme un texte annonçant un succès.

| Route | Contrat |
| --- | --- |
| `GET /v1/memories` | Chronologie paginée, curseur signé lié au lecteur/foyer ; objets rechargés et autorisés |
| `GET /v1/memories/{id}` | Souvenir courant ; 404 si privé, expiré ou effacé |
| `PATCH /v1/memories/{id}` | Texte requis ; champs omis conservés, `validUntil: null` retire l'expiration ; propriétaire et `If-Match` |
| `DELETE /v1/memories/{id}` | Tombstone, texte/étapes/origine effacés, époque incrémentée ; purge du vecteur asynchrone |
| `POST /v1/context` | `day` (`yesterday` ou date ISO), `key`, `query`, `limit` ≤ 8 et `maxCharacters` ≤ 12 000 |
| `GET /v1/commitments` | États et reçus actuels des tâches/actions accessibles ; pagination |

Mutations : `Idempotency-Key`. Une expansion du partage exige une preuve fraîche liée au corps normalisé via le step-up du socle. Pour PATCH, le hash porte sur les champs explicitement fournis (`MemoryPatch.model_dump(exclude_unset=True)`), y compris les valeurs nulles explicites ; le contenu fusionné avec le souvenir courant est validé avant écriture. Les champs inconnus sont refusés. Une clé de préférence/procédure est unique par propriétaire/type ; sa correction vise l'objet existant. Après expiration, POST peut remplacer la clé par un nouvel objet : gardes sur le souvenir et le slot empêchent un renouvellement concurrent de réactiver l'ancien objet après remplacement. Effacer l'ancien objet ne libère pas la nouvelle clé. L'origine liée doit être accessible ; une source privée ne devient pas une mémoire partagée. Les reçus d'idempotence ne conservent pas le texte.

« Hier » suit le fuseau du profil s'il est défini, sinon celui du foyer ; deux minuits locaux délimitent aussi les journées de 23/25 heures. Les index chronologiques/journaliers ne conservent que des références. Le contexte parcourt les partitions UTC de la plus récente à la plus ancienne, puis relit les sources et rapporte `sourceStatus=absent` lorsque leur accès a disparu. Bornes : 500 références d'archive, 20 candidats vectoriels, 8 souvenirs et nombre de caractères demandé. `truncated` signale une borne ; aucun rappel exhaustif n'est promis. Les recherches par clé relisent aussi les slots canoniques des préférences/procédures.

`KOYORI_SEMANTIC_MODE=simulated|disabled|aws` est choisi côté serveur. Le hash lexical local de 512 dimensions permet de tester les invariants et reste une **simulation**. En AWS : Titan V2 `amazon.titan-embed-text-v2:0`, 512 dimensions normalisées, S3 Vectors cosine `memory-v1`. Les filtres proviennent du contexte serveur ; droits, révision, époque, expiration et suppression sont vérifiés sur chaque candidat.

Le worker `projection` conserve une trace indépendante `MEMWORK` avant chaque écriture/effacement S3. Un effet ancien terminé après une correction/effacement réarme la projection canonique, même si elle était déjà terminée. Après interruption, la trace répare à 120 secondes ; le runtime Lambda de projection est borné à 60 secondes. Les purges sont prioritaires. Les échecs sont différés durablement avec délai croissant de 30 secondes à une heure, pour laisser progresser les autres foyers. Avant chaque requête Bedrock, un quota UTC de 200 tentatives par foyer est réservé atomiquement (`KOYORI_EMBEDDING_DAILY_LIMIT` côté serveur). Les retries automatiques Bedrock sont désactivés ; chaque nouvel essai requiert une nouvelle réservation. Les tentatives échouées comptent, et le quota épuisé reporte les projections au prochain jour UTC ; ce compteur n'est pas une facture.

Une projection réussie d'un souvenir temporaire planifie aussi sa purge à `validUntil`, même si l'expiration arrive pendant l'écriture fournisseur. La purge ne consomme pas d'embedding. Les anciens vecteurs expirés dont l'intention était déjà `DONE` sont réarmés sous garde lorsqu'ils sont rappelés : la première recherche peut rester vide jusqu'au passage du worker, puis les candidats vivants redeviennent accessibles. Les nouvelles projections n'exigent pas ce rappel préalable ; leur purge est déjà planifiée. La relecture canonique exclut les souvenirs expirés pendant ce délai.

En mode `disabled`, le worker termine les intentions de mémoire sous garde sans embedding ni vecteur, puis les retire du planning. Une activation ultérieure de la sémantique nécessite une reconstruction des projections ; ce changement n'ajoute pas de backfill automatique. Les jours explicites de contexte vont de `0001-01-02` à `9999-12-30` : les extrémités sans bornes civiles représentables sont refusées en 422.

## Capacités, budgets et actions

`GET /v1/capabilities` décrit `commerce.groceries`, `commerce.meals` (simulateur), `calendar.read` et `calendar.write` (Google), avec version, preuve attendue, accès, délais et règles de reprise. Une capacité sans configuration renvoie une indisponibilité explicite. Le commerce réel n'est pas admis. Le client ne choisit ni mode, ni prix, ni propriétaire, ni reçu.

`POST /v1/connections/simulated` crée un compte de recette persistant. `GET /v1/connections[/{id}]` et `DELETE /v1/connections/{id}` lisent/révoquent le compte privé à son propriétaire ; la révocation exige la révision. Elle bloque les nouveaux envois et les actions encore `READY`, tout en conservant le rapprochement des envois engagés.

`GET/PUT /v1/budget` : budget EUR par propriétaire et foyer, avec `limitMinor`, `perActionMinor`, `enabled`, `approvalRequired`. Les montants sont des centimes entiers. Première configuration : `If-Match: "0"`, ensuite révision actuelle. Une expansion ou la désactivation de l'approbation obligatoire exige une preuve fraîche. `spentMinor + heldMinor` ne dépasse jamais la limite ; réduire sous les engagements est refusé. La politique synthétique de l'étape 1 reste indépendante.

1. `POST /v1/quotes` : compte, capacité, `intentionId`, `operation=create|modify|cancel`, lignes et `deliveryAt` futur. Modifier/annuler exige `targetActionId` : dernière opération confirmée de la même intention. Le prix vient du fournisseur simulé. Le devis expire après 120 secondes ; l'empreinte couvre les conditions, le compte/époque et la version fournisseur.
2. `POST /v1/approvals` : `quoteId` et preuve fraîche. Approbation liée au devis exact, à la politique actuelle, à la génération d'accès et à l'expiration ; consommation atomique avec la réservation. Préférences, procédures et modèles n'accordent aucun droit.
3. `POST /v1/actions` : `quoteId`, éventuellement `approvalId`. `202` confirme seulement l'enregistrement atomique de l'action, réservation, verrou d'intention, événement et travail durable. `GET /v1/actions[/{id}]` expose progression et preuve.

| État | Signification et fonds |
| --- | --- |
| `READY` | Autorisé/réservé ; droits, politique et expiration revalidés avant envoi |
| `DISPATCHING` | Envoi engagé après écriture durable ; sans reçu, aucun succès établi |
| `UNKNOWN` | Réponse perdue/absente ; fonds conservés, recherche par clé fournisseur stable |
| `CONFIRMED` | Reçu vérifié ; fonds transférés aux dépenses confirmées |
| `CANCELLED` | Annulation prouvée par sa propre opération/reçu ; montant libéré selon ce reçu |
| `REJECTED` | Rejet prouvé ; réservation de cette opération libérée |
| `BLOCKED` | Droits/politique/expiration inadéquats avant envoi ; réservation non envoyée libérée |

Une même clé fournisseur ne produit pas deux mutations. Sans preuve, seul le rapprochement continue ; aucune commande n'est automatiquement renvoyée, ni remplacée pendant l'incertitude. La génération empêche un ancien worker de finaliser. Une modification réserve seulement une augmentation ; diminution/annulation affectent les dépenses après leur reçu. Le catalogue fictif contient lait, pain, fruits et deux repas ; aucun achat réel n'est effectué.

`POST /v1/webhooks/commerce-simulator` accepte `schemaVersion`, `eventId`, `householdId`, `actionId`, `occurredAt`. `X-Koyori-Signature` est HMAC-SHA256 du JSON trié compact, avec secret chiffré propre au compte ; fenêtre de cinq minutes et inbox anti-rejeu. Le signal réveille uniquement le rapprochement, y compris après révocation. Il ne devient jamais un reçu. Aucun secret de signature n'est exposé par HTTP.

## Google Calendar

Connexion : `POST /v1/connections/google-calendar/authorize` reçoit au plus huit `calendarIds`, exige une preuve fraîche et retourne l'URL OAuth. L'alias `primary` désigne l'agenda principal du compte, résolu après consentement grâce à l'entrée `primary` de la liste Google ; l'identifiant de cet agenda devient le libellé `account` de la connexion. `GET /v1/oauth/google/callback` vérifie l'état unique/expirant, échange le code avec PKCE, exige les deux scopes de lecture et les calendriers accessibles, puis chiffre les jetons par AES-GCM avec contexte propriétaire/connexion. L'idempotence sensible est également chiffrée. Un callback interrompu après consommation nécessite une nouvelle autorisation ; aucun code n'est rejoué aveuglément. Reconnecter le même compte remplace sa connexion active : l'ancienne est désactivée et son jeton effacé sans révocation chez Google, qui pourrait retirer l'accord tout juste renouvelé. Les propositions encore en attente ou approuvées suivent la nouvelle connexion du même compte, à condition qu'elle sélectionne toujours leur agenda (sinon `422 CALENDAR_NOT_SELECTED` à la confirmation, ou statut `FAILED` pour un ajout déjà approuvé).

`POST /v1/connections/{id}/sync` accepte un travail durable. `GET /v1/connections/{id}/events` revalide compte, jeton et calendriers accessibles chez Google, puis retourne la dernière synchronisation complète. Une page de 50 événements est appliquée sous bail/version ; les séries récurrentes sont développées en occurrences (`singleEvents=true`, compatible avec le `syncToken`). Un token expiré (`410`) lance une génération complète ; les anciennes générations ne sont plus restituées. Une synchronisation partielle n'est pas présentée comme complète. URLs encodées, redirections refusées, réponses bornées à 1 Mo.

Refresh sous bail de 30 secondes ; un retour après révocation ne remplace pas l'enveloppe. Révocation locale immédiate, puis révocation Google durable et effacement du jeton. Une révocation déjà demandée/achevée conserve sa révision lors d'une nouvelle DELETE avec la version courante. Le retour fournisseur `400 invalid_token` prouve que le jeton est expiré/déjà révoqué ; les autres échecs gardent `revokePending` et sont différés sans bloquer les autres comptes. Une erreur OAuth `invalid_client` ne révoque pas les droits de l'utilisateur. Les traces HTTPX/httpcore détaillant URL et en-têtes sont désactivées ; les erreurs structurées restent expurgées. Push : ID de canal, hash du channel token, resource ID, expiration et numéro de message. Les doublons/anciens signaux sont ignorés ; seuls les nouveaux signaux authentifiés réveillent une synchronisation. Renouvellement selon la durée effective du canal, avec une avance bornée à une heure ou à sa demi-durée, et polling à 60 secondes pour réparer les signaux perdus.

La perte d'appartenance au foyer, l'inactivation du profil personnel ou une nouvelle génération d'accès déclenche aussi la révocation locale et un nettoyage durable des jetons par le worker. Les snapshots d'autorité sont gardés dans la transaction ; une restauration concurrente invalide la décision. Une fois la révocation enregistrée, retrouver l'accès au foyer ne réactive pas le compte connecté. La révocation Google peut rester en attente pendant une panne ; elle reprend après redémarrage sans exiger un contexte utilisateur encore autorisé.

Avant `events.watch`, le worker conserve atomiquement les admissions `WATCH`/`CHANNEL` avec identité stable, token seulement hashé, statut `PENDING` et expiration demandée à deux heures. La notification initiale authentifiée peut fournir le resource ID et l'expiration effective avant la réponse et rendre l'admission active. La finalisation conserve le compteur des notifications et l'échéance la plus restrictive malgré les conflits ou une réponse tardive. Si le processus meurt ou si la réponse est perdue sans notification reçue, le même canal reste admis jusqu'à son expiration ; aucun nouveau canal n'est créé pendant l'incertitude. Le polling reste actif. Les watchs actifs sont renouvelés avec une avance bornée à une heure ou à la moitié de leur durée effective, calculée depuis l'admission durable : un TTL fournisseur court ne provoque pas une création à chaque passage. Ces contrats et les interruptions sont vérifiés avec un fournisseur factice, sans qualification Google réelle.

### Configuration et qualification externe

### Ajout d'événements (JRN-038)

Le scope `calendar.events.owned` est demandé en plus des deux scopes de lecture. Accordé, il ajoute `calendar.write` aux capacités de la connexion ; refusé lors d'un consentement granulaire, la connexion reste en lecture seule et toute proposition reçoit `409 CALENDAR_READ_ONLY`. Une connexion antérieure conserve ses seuls droits de lecture jusqu'à reconnexion.

Toute écriture passe par une proposition (`CALPROPOSAL`) : `POST /v1/calendar-proposals` (origine `person`) ou l'outil canal `propose_calendar_event` (origine `assistant`, voix et MCP personnels). Titre, début/fin en secondes UTC (durée de 1 s à 14 jours, fin future, début à moins d'un an), lieu et notes facultatifs ; agenda par défaut : celui du compte s'il est sélectionné, sinon le premier agenda sélectionné. Chaque changement de proposition émet `koyori.proposal.changed.v1`, autorisé pour le seul propriétaire dans l'activité. Rien n'est écrit avant `POST /v1/calendar-proposals/{id}/decision` (`approve` ou `reject`, `If-Match`), réservé au propriétaire ; aucun outil canal ne décide. L'interface enchaîne proposition et confirmation quand la personne remplit elle-même le formulaire ; si la réponse de confirmation se perd, une nouvelle tentative confirme la même proposition. Une heure sautée par le passage à l'heure d'été y est refusée ; une heure répétée prend sa première occurrence.

L'approbation crée un travail durable `CALWRITE`, exécuté par le rôle connecteur : revalidation de l'autorité et de la connexion, refus si l'agenda n'est pas possédé (`CALENDAR_NOT_WRITABLE`), puis `events.insert` sans notification d'invités (`sendUpdates=none`) dans le fuseau de la personne. L'identifiant Google dérive de la proposition (SHA-256 hexadécimal, inclus dans l'alphabet base32hex) et un `events.get` précède chaque insertion : une réponse perdue ou un nouveau passage retrouve l'événement au lieu de le dupliquer. Erreur réessayable : report exponentiel ; erreur définitive : statut `FAILED` avec code. Succès : `CREATED`, lien Google `https` conservé et synchronisation de la connexion réveillée.

`GET /v1/agenda?from=&to=` (31 jours au plus) agrège les événements de la dernière génération complète des connexions actives de la personne, journées entières converties dans son fuseau, au plus 200. `truncated` signale un agenda incomplet : première synchronisation d'un agenda encore en cours, ou parcours borné atteint (au plus 40 pages de 50 événements par connexion, dans l'ordre des clés) ; l'interface l'annonce au lieu d'afficher un agenda vide. Il ne rappelle pas Google : la synchronisation périodique revalide déjà l'accès et désactive une connexion retirée. Le callback OAuth répond par une page statique sans donnée de requête quand le navigateur demande du HTML (fenêtre de consentement), et `error=access_denied` y est expliqué ; les clients API gardent le JSON.

Local : client OAuth Web Google, Calendar API activée, callback loopback autorisé. Fournir `KOYORI_GOOGLE_CLIENT_ID`, `KOYORI_GOOGLE_REDIRECT_URI`, `KOYORI_GOOGLE_CONFIG_FILE` (fichier privé contenant `client_secret`) et éventuellement `KOYORI_GOOGLE_WEBHOOK_URL` HTTPS. Le bootstrap Docker conserve la clé dans `provider-key`, monté seulement dans l'API et le connecteur. Sur l'hôte : `KOYORI_TOKEN_KEY_FILE` pointe vers une clé aléatoire de 32 octets hors Git. Un override Compose local doit monter le fichier Google et transmettre ces variables aux rôles API/connecteur ; ne committer aucune valeur secrète.

AWS : table `Connections`, clé KMS à rotation et secret applicatif Google à renseigner. `KOYORI_GOOGLE_CLIENT_ID` est facultatif à la synthèse ; sans lui, Google reste indisponible. Le callback réel émis par API Gateway doit être enregistré chez Google. API/connecteur accèdent aux enveloppes ; workflows synthétiques, activité et projection n'ont pas le déchiffrement KMS. API/projection invoquent seulement le profil Titan retenu ; API lit l'index, projection écrit/efface.
